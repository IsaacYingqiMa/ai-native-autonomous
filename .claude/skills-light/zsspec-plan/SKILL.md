# zsspec-plan · 契约拆解为任务卡清单

产出一页 AI 可直接执行的任务卡：每张卡自足（做什么/怎么验/是否完成），按规格分组供 apply 并行调度。设计决策已在 spec「设计」定稿，plan 不重复、不预演代码级细节。本技能产出的唯一文件：`specs/active/<slug>/plan.md`。

> AI-Native 原则：任务卡跟着规格走（验证方式继承自 spec 验证行），分组跟着冲突域走；TDD 是步骤的一种写法，不是任务类型。

## 职权

| 边界 | 内容 |
|---|---|
| 只写 | `specs/active/<slug>/plan.md`（按本技能 `templates/plan.md` 模板写） |
| 只读 | spec.md、modules 的关键约束段（取回归命令）、项目既有测试/构建命令 |
| 越界去向 | 改规格或设计 → zsspec-spec；写代码或测试 → zsspec-apply |

<HARD-GATE>
1. 产出的唯一文件是 plan.md，禁止写任何代码或测试——计划是纸面作业。
2. 禁止覆盖重写已存在的 plan.md——已存在即停，交给 zsspec-apply（唯一例外见下方「修订模式」）。
3. 验证与用例继承自 spec（验证方式与 spec 验证行同源、不得改判；发现验证不合理或有缺口 → 停，提示回 zsspec-spec 修订模式）。
4. 用户点名要测试的任务，步骤必须含"转写用例 → 跑出断言失败 → 实现到全绿"；未点名的任务不引入测试步骤。
</HARD-GATE>

## 准入（任一不满足即停）

当前变更定位 = active/ 唯一未完成变更；多个时用户点名或列出清单（slug + 一行进度）让用户选。

| 条件 | 不满足时 |
|---|---|
| spec.md 存在且「冲突声明」为"无" | 冲突为"有" → 停止等用户裁决，经 zsspec-spec 修订模式落实后重进 |
| spec「设计」四项齐全 | 缺失 → 回 zsspec-spec 补写 |
| plan.md 不存在 | 已存在 → 回复"计划已存在，请说'继续'进入执行" |

**修订模式**（HARD-GATE 2 的唯一例外）：plan.md 已存在、且存在待落实的用户裁决（apply T2 答案或用户打断纠偏）时——按裁决修改或增删**未勾**任务卡（新增行天然未勾）；已勾任务卡是既成进度，一律不动；阶段报告声明改了哪些卡，修订完回 zsspec-apply 从第一个未勾任务继续。

## 产出模板（plan.md 的唯一定义）

按本技能 `templates/plan.md` 产出：按 Sx 分组（组头 `### Sx <规格名> · 未开始`，状态三态由 apply 刷新）+ 任务卡。禁止保留占位符与模板注释；模板缺失 → 停止并提示"技能包不完整，请重新拷贝 zsspec-plan 技能目录"。

**任务卡结构（四层 + 状态）**：
- 状态 = 任务勾选（`[ ]` 未勾 / `[x]` 完成）+ 组头三态（未开始 / 进行中 / 已完成，apply 刷新）
- **描述**：一句话范围与边界
- **步骤**（可选层）：关键步骤列表（1–3 条，做什么层面，不写代码级细节）；简单任务省略本层
- **预期**：可判定的现象/结果（与 spec 验证行的预期一致；有用例的对齐用例）
- **验收**：留空占位，apply 编码后回填实际观察（具体现象/输出/判定，禁只写"通过"）

**TDD 体现（仅点名/测试验证的规格）**：步骤写法为"1. 把 spec 用例转写为 <测试文件>，跑出断言失败 2. 实现至用例全绿"，预期 = "测试 N/N 全绿"。

## 流程

1. **按 spec 规格分组，一规格至少一卡**：复杂规格拆多卡（Sx-1、Sx-2…，按可独立验收的单元拆）；分组同时核对文件归属（见下条）
2. **组 = 冲突域（为 apply 并行铺路）**：按 spec「设计 · 模块与接口」清单核对，两组任务触及同一文件 → 合并为一组，或在报告中标注"该两组须串行"；无法判定文件归属时保守合并
3. 每卡四层按结构写：预期与 spec 验证行同源；步骤只写关键步骤（TDD 步骤仅用于点名/测试验证的规格）
4. 首尾固定：「准备」组仅当**存在测试任务且项目无测试设施**时保留（P1 搭建测试设施，验证 = 框架 smoke 跑通；无测试任务不建）；末尾固定「回归」组（R1 = 重放全部验证：构建命令全跑 + 运行核验任务重放用例核对 + 测试全跑）
5. 不预演代码级细节：文件级改动由 apply 按 spec「设计」自主决定——plan 只锁任务与判定
6. 任务卡很多（如一个规格拆出大量卡）→ 不硬拆，报告建议用户拆分需求分次推进，照常单计划走完

## 门禁（写入前逐项核对，全过才写）

- [ ] 每个 Sx 组头带状态（初始"未开始"）；每张卡有描述与预期（可判定），验收行留占位；简单卡无步骤层，复杂卡步骤 ≤3 条且无代码级细节
- [ ] 每卡有编号（Sx-n / P1 / R1）；预期与 spec 验证行同源，无改判
- [ ] 测试步骤仅出现在 spec 验证为测试或用户点名的任务；点名任务的步骤含"转写用例 → 跑出断言失败 → 实现到全绿"
- [ ] 组间无同一文件被两组触及（有则已合并或标注串行）
- [ ] 末组为「回归」；存在测试任务且无测试设施时首组为「准备」

## 阶段报告

三行简报：**做了什么**（一两句：任务卡数、测试任务数、可并行组）/ **需要注意**（须串行的组、推断待校验的命令、高风险任务，无则"无"）/ **下一步**（建议进入 zsspec-apply）。
输出后：自动模式（用户已授权）→ 直接进入 zsspec-apply；默认 → 停，等用户说"继续"或指定技能。
