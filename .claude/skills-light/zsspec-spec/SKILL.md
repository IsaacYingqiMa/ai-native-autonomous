# zsspec-spec · 需求、规格与设计（形成契约）

把一项开发意图变成完整契约：需求（为什么）→ 边界（范围）→ 规格（做什么/规则/用例/验证）→ 设计（怎么做）。功能点级到模块级/系统级需求同一结构承载。本技能产出的唯一文件：`specs/active/<slug>/spec.md`。

> AI-Native 原则：spec 出题、apply 答题——验证方式直接写在规格里（无档位路由），默认运行核验与构建验证，测试只在用户点名或核心资产时使用；证据按风险付费。

## 职权

| 边界 | 内容 |
|---|---|
| 只写 | `specs/active/<slug>/spec.md`（按本技能 `templates/spec.md` 模板写） |
| 只读 | `specs/MAP.md`、涉及模块的 `specs/modules/*.md`、必要时 src/ 对应代码、用户需求 |
| 越界去向 | 改 modules → zsspec-archive；拆任务 → zsspec-plan；写代码 → zsspec-apply |

<HARD-GATE>
1. 产出的唯一文件是 spec.md——写其他任何文件即越界。
2. 用户提过的需求被剔除时必须落入「边界 · 不做」并附理由，禁止静默删除。
3. 代码与需求矛盾必须写入「冲突声明」并停止等用户裁决，禁止自行调和。
4. 验证方式与规则强度匹配：规则含分支/校验/计算逻辑的，验证不得只写构建（运行核验起步）；仅静态呈现的可只写构建。
5. 影响一或多条例规格走向、且无唯一答案的决策，默认模式必须经「关键决策确认」由用户拍板，**禁止静默拍板**；自动模式逐项按推荐项拍板并全部落档（取舍 + 报告清单）——spec 任何段落不得残留"待定/开放"。
</HARD-GATE>

## 准入（任一不满足即停）

| 条件 | 不满足时 |
|---|---|
| `specs/` 存在 | 回复"先运行 zsspec-init" |
| slug 不与 `specs/active/` 既有变更目录及 INDEX.md 已有重复 | 换 slug（kebab-case，创建后不改） |

**多变更并存**：active/ 有未完成变更**不阻断**开新变更——两者可并行推进（各有独立 spec/plan，"继续"时多个变更由用户点名或列清单选择）。仅一项软检查：新变更「受影响模块 / 设计 · 模块与接口」与既有 active 变更涉及相同模块或文件时，报告提示"与 active 变更 <slug> 重叠 <模块>——并行有冲突风险，建议先收口其一"，提示不阻断，用户自行决定。

`active/<slug>/spec.md` 已存在但不完整（门禁未过、设计缺失）→ 属同一变更，续写补全（不新建目录、不适用修订模式）。

**修订模式**（准入表与续写之外的唯一例外进入方式）：active/<slug>/spec.md 已存在、且存在待落实的用户裁决（apply T2 答案、冲突声明裁决或用户打断纠偏）时，不新建变更——按裁决单点修订对应条款，并在「记录」段头追加一行 `> 修订：<日期>：<简述>`（冲突声明裁决落实后把「冲突声明」改为"无"）；除裁决内容外禁止改动；修订完回 zsspec-apply 从第一个未勾任务继续。

## 产出模板（spec.md 的唯一定义，不引入其他格式）

按本技能 `templates/spec.md` 逐段产出真实内容，禁止保留占位符与模板注释；模板缺失 → 停止并提示"技能包不完整，请重新拷贝 zsspec-spec 技能目录"。模板管形状，以下规则模板未覆盖：

1. 规格编号 S1、S2… 创建后不改；规格名为动宾短语（如"发起售后申请"），可辨识即可
2. **规则** = 触发 → 结果 的箭头断言列表（失败路径就是一种规则，不单列）；禁止"应该/尽量/考虑"类含糊词
3. **用例**（可选）：表驱动"场景/输入/期望"，是预期的精确化——有行为逻辑的规格建议写（运行核验按它逐条对，测试按它转写）；仅静态呈现的规格省略
4. **验证**四种写法（按规格性质自然选择，无档位）：
   - 构建：`npm run build` → 零报错（静态/结构类）
   - 运行核验：运行 <入口>，<操作> → <预期观察>（行为逻辑类默认）
   - 测试：`pytest tests/xxx.py -q` → 全绿（**仅当**用户点名要测试、或规格触及知识层标记的核心资产时）
   - 达标：评测脚本/命令 → <指标阈值>（调优/涌现类）
5. 「设计」在规格定稿后写，深度到方案级、不到逐行代码；「模块与接口」清单 = apply 的**结构边界**（接口/模块/数据结构），不是文件白名单——支撑性小改（辅助文件/配置/类型声明）授权 apply 自行处理并申报，结构性新增必须回本技能修订
6. **修改优先**：对既有功能的变更，「修改」清单是常态——对照知识层契约或 src 既有代码定位后修改；「新增」仅限全新业务能力或经论证的失衡，理由落「取舍」。涉及既有代码必须先读该代码（modules 或 src），**禁止未读即拍新增**——绕开旧实现另起一套 = 重复实现 + 僵尸代码
7. 「记录」两段（知识维护 / 冲突声明）是流程附录，交给 zsspec-archive 消费

规格小节实写样例（对齐这个质量写）：

```markdown
### S1 发起售后申请

- 做什么：对"已完成"订单发起售后申请，创建售后单并锁定重复发起
- 规则：
  - 完成后 15 天内发起 → 创建售后单（pending）
  - 完成超 15 天发起 → 拒绝创建，提示不可售后原因
  - 同一订单已有进行中售后单再发起 → 拦截
- 用例：
  | # | 场景 | 输入 | 期望 |
  |---|---|---|---|
  | 1 | 正常发起 | 完成第 10 天提交 | 生成 pending 售后单 |
  | 2 | 超期发起 | 完成第 16 天提交 | 拒绝并提示原因，无售后单 |
  | 3 | 重复发起 | 已有 pending 单再提交 | 被拦截 |
- 验证：运行售后申请页按用例 1–3 核验（用户点名测试锁定：`pytest tests/after_sale/test_apply.py -q` → 全绿）
- 依据：`src/order/service.py::get_order_status` · 覆盖：期望结果

### S2 公司介绍页

- 做什么：公司简介、发展历程时间线（≥3 节点）、资质摘要，占位文案
- 验证：`npm run build` → 零报错且 dist/ 产出
- 依据：新接口 · 覆盖：期望结果（关于我们）
```

## 流程

1. 读 `specs/MAP.md` → 按需求（对照核心实体列）读 1-3 个 `specs/modules/<name>.md` → 知识不足时读 src/ 对应代码
   - 因知识层缺失而读代码、或 modules 与代码不符 → 记入「记录 · 知识维护」（只记录，不修改）
2. **校准检查（仅当「受影响模块」非空——即变更触及既有代码；全新项目/无既有模块直接跳过）**：对读过的每个模块（代码路径取其「代码」行），以校准头为基线对账——`git log --oneline --since=<校准头日期> -- <代码路径>`（init 或 slug 均按日期）。存在无法归属 INDEX 任何 slug 的提交（流程外变更）→ 本变更依赖的契约逐一对照代码核实后才可作规格依据，差异记「记录 · 知识维护」，报告提示"模块 <name> 存在流程外变更"
3. 需求定义（5 字段）
4. **关键决策确认（判据见 HARD-GATE 5）**：收集"影响一或多条例规格走向、且无法从需求/知识层/既有代码确定唯一答案"的决策点（技术选型、范围边界、非功能要求、数据/文案口径等）——
   - **默认模式**：一次性批量抛给用户，每题 = 明确问题 + 2–4 个选项 + 推荐项置首（附一句理由），逐项确认或改选；答案落入「边界」与「设计 · 取舍」；决策点 >6 个分批（先问影响最大的）
   - **自动模式**：不问，逐项按推荐项拍板，全部写入「设计 · 取舍」，报告列**自主拍板清单**（决策 + 所选 + 理由）供事后纠偏——文档收敛，禁止留"待定"
   - 无此类决策点 → 跳过本步
5. 写「边界」（不做项各附理由）；逐项质疑："不做它，哪个具体结果会失败？"答不出的剔除，落入「边界 · 不做」（附理由）
6. 写规格 S1、S2…（按产出模板；规则为箭头断言、验证方式按性质选择、用户未点名不主动写测试验证）
7. **阻断性追问（即时兜底）**：写规格过程中遇到新的含糊点且无法自答 → 单点追问（选择题式 + 推荐项），答后继续
8. **盲推对照（仅规格数 >5 时做；小变更跳过省 token）**：开全新上下文（子代理），仅喂「需求」段原文 + 相关 modules 契约（不喂已写规格草稿），令其独立输出 3–5 个"该需求最该被验证的可观测结果"；与各规格「规则 + 用例」逐条对照——盲推项无对应规格 → 补规格或记「边界·不做」；某规格规则/用例无盲推锚点 → 回写或删；盲推产出中可枚举的"输入→期望"直接补进对应用例表；不能自答的分歧进「记录 · 冲突声明」阻断等裁决。对照结论写入阶段报告「需要注意」。
9. 写「设计」（基于已读知识层与代码；模块与接口清单 = apply 改动边界；关键决策确认的答案落入「取舍」）
10. **规模自检（软建议，不阻断）**：规格数 > 10 → 报告提示"规模较大，可拆分次推进（附建议切分）"，照常单变更走完

## 门禁（写入前逐项核对，全过才写）

- [ ] 需求段每项有"不做的后果"；「边界」不做项各有理由
- [ ] 关键决策已确认：默认模式全部经用户拍板（无静默拍板）；自动模式已按推荐项拍板并落「取舍」，报告含自主拍板清单；spec 无"待定/开放"残留
- [ ] 规则为箭头断言（触发 → 结果），无"应该/尽量"；规则含分支/校验逻辑的，验证为运行核验/测试/达标（未只写构建）；静态规格验证为构建即可
- [ ] 验证行四写法之一，可执行可判定；测试验证仅出现在用户点名或核心资产场景（未点名时报告已提示"如需测试锁定请点名"）
- [ ] 有用例的规格：每条规则至少被一个用例覆盖
- [ ] 规格 >5 条时盲推对照已完成，漏项/偏题项已处理（补规格 / 补用例 / 记不做 / 修订 / 裁决）
- [ ] 涉及现有接口的规格有代码依据
- [ ] 「设计」四项齐全：方案 / 模块与接口（现有接口有依据）/ 数据与状态 / 取舍
- [ ] 修改优先：涉及既有功能的规格，「修改」清单已对照 modules/代码定位既有结构；「新增」项均有理由（全新能力或「取舍」中论证），无"未读代码即新增"项
- [ ] 剔除项全部落入「边界 · 不做」并附理由；冲突声明为"无"（"有"则已阻断等待裁决）

## 阶段报告

三行简报：**做了什么**（一两句：需求与规格条数、验证方式分布）/ **需要注意**（剔除项及理由、开放问题、风险；**自动模式下列自主拍板清单**（决策 + 所选 + 理由）；含测试锁定建议——核心资产规格未点名测试时提示"如需测试锁定请点名"，无则"无"）/ **下一步**（建议进入 zsspec-plan）。
输出后：自动模式（用户已授权）→ 直接进入 zsspec-plan；默认 → 停，等用户说"继续"或指定技能。
